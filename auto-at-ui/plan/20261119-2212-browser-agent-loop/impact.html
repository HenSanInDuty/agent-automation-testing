Engine agent loop cho Vision

Thêm engine Vision thứ hai chạy theo vòng lặp khép kín kiểu browser agent (paper arXiv 2511.19477): quan sát → model tự đánh giá bước trước, ghi memory, chọn hành động trên ref có version → thực thi → quan sát lại. Engine hiện tại (planner, v4) giữ nguyên và vẫn là mặc định. Test case "click hết control" của mongchiton chạy được như một task bình thường trên engine mới, chấm bằng benchmark độc lập như cũ.

Khảo sát: reports/survey/be-control-plane.md, be-worker.md, fe-dashboard.md. Mọi mục đều áp dụng.

AContract

Outcome

Chọn engine=agent_loop khi tạo session. Mỗi bước: worker trả snapshot mới (ref dạng version:n), model trả evaluation_previous_goal, memory, next_goal và 1..N action (hoặc done/stop/need_screenshot). Control-plane kiểm an toàn bằng code, chạy từng action qua đường operation có sẵn (frame before/after), dừng batch khi trang đổi, ghi step log, lặp. Không restore, không replay: agent đi tiếp từ trang hiện tại, back/navigate là tool của model.

Constraints

  • Quy tắc tầng của AGENTS.md; prompt chỉ ở agents/prompts/ có version + README; contract chung ở packages/contracts; Python qua uv.
  • v4 không đổi hành vi, không đổi schema hash của codex-dom-v11; mọi nới guard ở worker đặt sau cờ engine.
  • Provider giữ nguyên (codex_cli, claude_cli qua bridge hiện có).
  • Evidence tương thích run.py collect/evaluate; metrics.py và oracle không đổi.
  • Ngân sách: số lần gọi model, rate/phút, thời gian session, trần ký tự snapshot.

Non-goals

  • Không dùng model nhẹ để cắt snapshot (cần chọn provider mới); chỉ cắt tất định.
  • Không bỏ hay viết lại v4; không đổi metrics/oracle.
  • Không multi-tab ngoài cơ chế một popup hiện có; không game thời gian thực/canvas.
  • Không giữ phiên CLI sống giữa các bước (cần ADR bảo mật riêng).
  • Không cam kết miễn nhiễm prompt injection.

Acceptance criteria

  1. Session agent_loop chạy vòng lặp; mỗi lần gọi model chỉ nhận snapshot mới nhất + memory + K bước gần nhất; step log lưu evaluation/memory/next_goal/actions.
  2. Ref của snapshot cũ bị từ chối an toàn, không có hành động trình duyệt.
  3. Hành động trên trang ngoài allowlist, nút submit/download/từ khoá nhạy cảm bị chặn bằng code và được ghi lại.
  4. Batch dừng các action còn lại sau action làm đổi trang và lấy snapshot mới.
  5. Input mỗi lần gọi bị chặn trên (cap snapshot + marker [refs a-b trimmed] + nén lịch sử).
  6. Task click-hết-control mongchiton chạy trên agent_loop; run.py collect + evaluate sinh score.json không sửa metrics/oracle; không kết thúc bằng unsafe_replay.
  7. Toàn bộ test hồi quy v4 xanh; engine mặc định vẫn là planner.

ELuồng dữ liệu

  1. Entry: POST /explorations {engine: "agent_loop", ...} → validate (cờ bật, provider bridge, target thuộc allowed_origins của project) → session row exploration_engine=agent_loop, trace_version="v4" (giữ để lease/trace/dashboard chạy) → outbox event. Đồng bộ, một transaction.
  2. Dispatch: temporal-worker poll → vision_publisher đọc session → VisionAgentLoopProcessor. Bất đồng bộ, có lease.
  3. Open + setup: worker.open (agent_mode, origin_policy) → op navigate purpose setup (frame + checkpoint).
  4. Observe: worker.observe_dom → control-plane đánh số version:n → map RAM {(version,n) → (snapshot_id, element_id)}. Biến đổi shape: element id 32 hex thành ref ngắn; cắt theo trần ký tự, chèn [refs a-b trimmed].
  5. Decide: CodexCallBudget.reserve → CodexModelBatch (prompt agent-loop-v1, agent_context = task, allowlist, memory, K bước gần nhất, snapshot) → spool → CLI → AgentLoopOutput. Bất đồng bộ qua file spool, ~41 s/job.
  6. Guard: ref sai version → từ chối (không gọi worker); vision_agent_safety → chặn/ghi lý do.
  7. Act: mỗi action → state/proposal/edge (uow.proposals) → ExecuteVisualOperation (prepare, before frame, ack, execute, after frame) purpose explore, binding dom_snapshot_id/dom_element_id → worker chặn lần hai (allowlist, submit/download, stale). Side effect: hành động trình duyệt, frame lên RustFS.
  8. Stop batch khi fingerprint đổi, url_change, popup, download, hoặc lỗi.
  9. Record: visual_agent_steps (fenced write) + activity agent.step. Transaction boundary: mỗi step một commit.
  10. Loop về bước 4 tới khi done/stop/hết budget → uow.finish(reason); /result, /trace phục vụ dashboard và run.py collect.

FLuồng nghiệp vụ

Actor: người kiểm thử hoặc benchmark harness. Tiền điều kiện: project có allowed_origins chứa target; tenant policy chọn provider bridge; cờ VISION_AGENT_LOOP_ENABLED bật; bridge host đang chạy.

  1. Gửi task (ví dụ "click thử tất cả các nút trên trang chủ và kiểm tra trang đích"), chọn engine agent loop.
  2. Agent mở trang, nhận snapshot, lên kế hoạch trong memory, gửi batch action.
  3. Rẽ nhánh sau mỗi action:
    • Trang không đổi → action kế trong batch.
    • Trang đổi / popup mở → dừng batch, snapshot mới, model đánh giá (ví dụ "popup Tepaylink mở đúng, đóng và quay lại").
    • Popup/trang ngoài allowlist → xem K3: chỉ quan sát, mọi action trên đó bị chặn trừ đóng/quay lại.
    • Action bị chặn (submit, download, từ khoá) → không chạy, kết quả "blocked" trả về model ở bước sau.
    • Ref cũ → "stale_ref", model phải dùng snapshot mới.
  4. Model tự đánh giá kết quả bước trước. Thất bại thì không lặp y hệt, phải đổi cách (ví dụ carousel PREVIOUS không đổi slide → thử lại một lần bằng chấm indicator).
  5. Kết thúc khi model trả done, stop, hoặc hết budget/thời gian.

Đường lỗi: bridge timeout / schema sai → một lần retry rồi dừng có lý do; worker action_outcome_unknown → khoá session như v4; mất lease → dừng an toàn. Hậu điều kiện: step log + operations + frames đầy đủ; conclusion partial / not_established (engine mới không có inventory toàn trang, không tự nhận "completed"). Biên: trang chỉ có canvas → need_screenshot; trang > 100 control → marker trimmed + cuộn; form nhiều ô → batch type nhờ re-baseline.

GMàn hình / UI

  • Form tạo exploration (vision-dashboard.tsx): thêm một <select> Engine (Planner mặc định / Agent loop), chỉ hiện khi API báo cờ bật. Không thêm ô allowlist (dùng allowed_origins của project).
  • Chi tiết session: ledger operation hiện có hiển thị thêm khối nhỏ theo bước: đánh giá bước trước, memory, mục tiêu kế. Action bị chặn hiện thành dòng "blocked" với lý do.
  • Mã lỗi mới (stale_ref, origin_blocked, sensitive_action_blocked, agent_step_limit) có câu hiển thị riêng trong vision-provider-model.ts.
  • Loading / empty / error / không quyền: tái dùng trạng thái có sẵn. Không đổi bố cục; điều khiển bàn phím của ledger giữ nguyên.
  • Sửa nhãn "advisory, model proposals only" cho session agent loop vì engine này thực thi thật.

KRủi ro & câu hỏi còn treo

K1. Trần 20 lần gọi model mỗi sessionNằm ở 6 chỗ (policy, step guard, request_sequence request/response, CHECK DB, activity). Round 21 v4 dùng 20 lần cho 47 click. Agent loop dừng batch mỗi khi popup mở (25/47 target là popup), nên 20 bước có thể không đủ cho task click-hết-control.
Đề xuất: giữ 20 cho phase 1–5, đo ở phase 6; nếu thiếu thì thêm phase nâng trần riêng cho agent loop (v4 vẫn 20).
K2. Tool mới của paper (hover, press_key, select_option, wait_for text, navigate tới URL tuỳ ý)Mỗi tool đổi enum contract worker, TS và evidence.py của benchmark.
Đề xuất: đợt đầu chỉ dùng kind có sẵn (click, type, scroll, wait, back, close_popup, navigate về target); tool mới để plan sau (mục L).
K3. Allowlist và popup ra ngoàiTest case mongchiton cần popup sang Facebook, Tepaylink, TestFlight, Google Play mở được để chấm "trang đích". Chặn cứng theo allowed_origins của project sẽ làm hỏng test case này.
Đề xuất: điều hướng/popup ngoài allowlist được mở để quan sát, mọi action trên đó bị chặn trừ đóng/quay lại; sub-resource (ảnh, CDN) không chặn. Allowlist lấy từ project, không thêm cột theo session.
K4. Lỗi dialog/downloadHiện một dialog hay download không rõ chủ khoá vĩnh viễn session.
Đề xuất: ở agent mode, dialog/download do chính action gây ra được ghi lại, huỷ và báo model; action_outcome_unknown vẫn khoá như v4.
K5. Retention và reloadĐề xuất: step log theo intent_retention_until của session; reload giữ engine của session gốc.
Rủi ro
  • ~41 s/job bridge → 20 bước ≈ 14 phút model; bulk action là điều kiện cần.
  • Working tree có ~55 file sửa chưa commit trên đúng đường đi (codex_bridge, codex_candidates, vision_trace_events, rustfs…). Phải xử lý ở phase 0, nếu không merge sẽ lẫn.
  • Detection precision/recall của benchmark lấy từ inventory trang; agent loop không quét toàn trang nên điểm detection có thể không so được với v4. Coverage/accuracy vẫn so được.
  • Phase 6 chạy live gọi model thật (subscription), cần bạn cho phép lúc chạy; token Claude bridge hết hạn ~2026-11-20 03:50.
  • Chi phí grounding khi nâng trần > 100 phần tử chưa đo.

LLược bỏ (YAGNI)

Đã bỏ khỏi thiết kế

  • Bỏ model nhẹ cắt snapshot — thêm khi snapshot thực tế vượt trần và bạn chọn provider.
  • Bỏ endpoint snapshot theo range ở worker — snapshot đã nằm ở control-plane, render range tại đó.
  • Bỏ endpoint batch ở worker — per-op giữ frame before/after cho benchmark; tiết kiệm chỉ vài round trip.
  • Bỏ ariaSnapshot() làm nguồn ref — Playwright 1.50 không trả ref hay handle.
  • Bỏ giữ phiên CLI sống, multi-tab, cột allowlist theo session.
